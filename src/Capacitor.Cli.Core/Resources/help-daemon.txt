kcap daemon — Manage the daemon process

Usage: kcap daemon <subcommand>

Subcommands:
  start [-d]              Start the daemon (foreground, or -d for background)
  stop [--name N] [--yes] Stop a running daemon (prompts on multi unless --yes)
  restart [--name N]      Restart the daemon (now if idle; --when-idle queues;
                          --force overrides while busy)
  status [--name N]       Show daemon status, incl. the running daemon's
                          version (lists all when --name omitted)
  logs                    Show recent daemon log output
  doctor [--clean]        Diagnose lock-file state, optionally clean stale entries
  service <action>        Manage the OS service (launchd/systemd/Scheduled Task)
  shim <action>           Manage the command-line tool (kcap on your terminal PATH)
  consent <verb>          Manage the launch-consent policy (see "Consent" below)

Options for start:
  --name <name>           Daemon name (defaults to OS username)
  --server-url <url>      Server URL
  --max-agents <n>        Max concurrent hosted coding agents (default: 5)
  --log-file <path>       Log to file instead of console
  --log-level <level>     Log verbosity: trace|debug|information|warning|error|
                          critical|none (default: information). Also settable via
                          KCAP_DAEMON_LOG_LEVEL; the flag wins when both are set.
                          Use debug for transport diagnostics (e.g. DaemonPing RTT).
  -d, --detach            Run in background (logs to file automatically)

Options for stop:
  --name <name>           Stop just the named daemon. Without it, all daemons
                          are listed and the command asks for confirmation
                          before stopping them (unless --yes is passed).
  --yes, -y               Unattended mode: stop all running daemons without
                          prompting. Useful in cleanup scripts.

Options for restart:
  --when-idle             Queue the restart; it applies once the daemon is idle
                          (no running hosted agents or eval). Returns immediately.
  --force                 Restart now even if busy (running agents are torn down).

Updating: after `kcap update`, a running daemon on macOS/Linux detects the new
binary and restarts itself when idle. `kcap daemon status` reports the running
daemon's version plus any pending restart, so you can confirm a self-update took
effect. On Windows, stop the daemon before `kcap update` (a running daemon locks
its binary).

Options for doctor:
  --clean                 Remove stale entries (lock files whose holder is
                          gone). Held entries are never touched. Without
                          --clean, doctor reports state without modifying.

Subcommands for service (per-user; auto-restarts on crash/SIGKILL, starts at login):
  install [--name N] [--profile P] [--max-agents N] [--no-start] [--replace] [--verify]
                          Register the daemon as an OS service and start it.
                          Pins the profile via KCAP_PROFILE and captures PATH so
                          claude/codex resolve as they do in your shell. --verify
                          (macOS/launchd only; rejected elsewhere) polls readiness
                          (hello), version, and ownership (job pid) before
                          exiting 0, rolling back (uninstalling the unit) and
                          exiting with a coded stderr token (e.g.
                          verify_hello_validation) if that never happens within
                          the poll budget. --replace (requires --verify) takes
                          over an existing label/unit — clears a foreign/loaded
                          label, stops a validated live owner, then installs.
                          --no-start cannot be combined with --verify (verify
                          proves the STARTED daemon is ready).
  uninstall [--name N]    Stop and remove the service unit.
  start [--name N] [--verify]
                          Start the installed service now. --verify (macOS/
                          launchd only; rejected elsewhere) polls readiness
                          (hello) and ownership (job pid) before exiting 0,
                          rolling back and exiting with a coded stderr token
                          (e.g. verify_readiness_timeout) if the service never
                          comes up within the poll budget.
  stop [--name N]         Stop the running service (unloads/deregisters it with
                          the OS supervisor; stays installed — returns at next
                          login or `service start`).
  ensure [--name N] [--profile P] [--json]
                          Flow-driven ladder: from a fresh status read, install
                          when there is no unit (baking the born-prompt consent
                          directive) or start when the unit is present but
                          stopped; "already enabled" when the daemon is running
                          (on launchd only when the service job owns the
                          validated daemon pid). On macOS/launchd both arms run
                          the verified transaction, so a gate refusal exits with
                          the coded verify exit plus start_gate_reason=, mapped
                          to recovery_surface=takeover|reinstall|attention —
                          never guessed from prose; coded viability/refusal
                          reasons route likewise (package_inconsistent →
                          reinstall, boot refusals → storage/takeover), and
                          refused launchd transactions report verified:true.
                          Windows/Linux degrade to plain install/start (no
                          gates; --json reports verified:false). macOS requires
                          a resolvable profile (no_profile_configured refusal
                          otherwise). Ambiguous states (unknown probe, active
                          transaction, orphan label — running included — stale
                          marker) fail closed to attention with a coded reason
                          — never mutated into.
  status [--name N] [--json]
                          Show installed / running state. --json emits a
                          machine-readable snapshot (service/job/daemon pids,
                          binary paths, transaction-marker state) and exits
                          non-zero if the underlying service state can't be
                          determined.

Subcommands for shim (the command-line tool — kcap on your terminal PATH):
  ensure [--json]         Probe the login shell. If kcap already resolves
                          from the terminal, report already_on_path and exit
                          0. If it is absent, link /usr/local/bin/kcap to this
                          CLI (macOS only; prompts once for your admin
                          password, then re-probes so success is never
                          reported on the symlink alone). Every ambiguous row
                          fails closed with a coded reason: an unknown probe
                          (probe_unknown), a different filesystem entry at the
                          destination (conflict), or an unsupported platform
                          (unsupported_platform) — nothing is ever guessed or
                          overwritten. --json emits the outcome + coded reason
                          the flow keys off (e.g. installed, refused).
                          Exit 0 only when the terminal now resolves kcap.

Consent:
  Every SERVER-driven launch (a coding agent, PR review, or review-flow
  participant started from the dashboard) is checked against a daemon-owned
  launch-consent policy before it runs. Launches from the daemon's own local
  socket (`kcap agent start`) are always the owner's and never consult this
  policy. The daemon owner is ALWAYS allowed, regardless of the policy below
  — this built-in bypass cannot be turned off. For everyone else, rules are
  checked in order and the FIRST MATCH WINS; a request that matches no rule
  falls through to the policy's default. A denial surfaces to the server (and
  the requester) as the coded reason `launch_denied_by_owner`.

  kcap daemon consent show                       Print the current default,
                                                   prompt timeout, and every
                                                   rule with its index
  kcap daemon consent set-default <allow|deny|prompt>
                                                   Set the fallback verdict
                                                   for a request no rule
                                                   matches:
                                                     allow  — let it through
                                                              (upgrade-safe;
                                                              every daemon
                                                              starts here)
                                                     deny   — reject it
                                                     prompt — ask the daemon
                                                              owner, and deny
                                                              on timeout / no
                                                              approval UI
                                                              attached
  kcap daemon consent allow [--requester U] [--kind agent|review|review-flow]
                             [--repo PATH] [--vendor V]
                                                   Append an "allow" rule
  kcap daemon consent deny  [--requester U] [--kind agent|review|review-flow]
                             [--repo PATH] [--vendor V]
                                                   Append a "deny" rule
  kcap daemon consent remove <index>              Remove the rule at the
                                                   index printed by `show`
  kcap daemon consent log [-n N]                  Tail N lines (default 20)
                                                   of consent-decisions.jsonl
                                                   — a direct file read, so
                                                   it works with the daemon
                                                   stopped

  `show`/`set-default`/`allow`/`deny`/`remove` mutate the policy over the
  daemon's local socket and require a running daemon. `allow`/`deny` require
  at least one of --requester/--kind/--repo/--vendor — an omitted field is a
  wildcard (matches anything), so a flagless "allow" would be a permanent
  no-op, and a flagless "deny" is already expressible as `set-default deny`.
  --repo accepts an exact path or a "/prefix/*" glob. All six verbs take
  --name <n> like the rest of `kcap daemon`.

Notes:
  Each daemon holds an exclusive flock on ~/.config/kcap/daemons/<name>.lock
  for its entire lifetime. The kernel releases the lock automatically on
  process exit (including SIGKILL or power-off), so stale lock files on disk
  are never a blocker — only a live process holding the kernel-level lock
  can prevent another daemon from acquiring the same name.

  Two daemons with different --name values can run side-by-side. Two daemons
  under the same name on the same machine collide on the flock and the
  second one exits with code 2. If they somehow both connect to the server
  anyway, the server-side check rejects the second one with exit code 3.
