# Task 14 report — kcap-cli: validate-plan artifact endpoint + workspace_root emission

## Commit
- `9f3fac6` on branch `alexeyzimarev/ai-701-validate-plan-artifacts` (local only, not pushed).

## What changed

### 1. ValidatePlanCommand two-call flow (`src/Capacitor.Cli/Commands/ValidatePlanCommand.cs`)
- `Handle` now delegates to a new testable `HandleCore(HttpClient, baseUrl, sessionId)` seam
  (mirrors `ClaudeHookCommand.HandleCore`).
- Calls `GET /api/sessions/{id}/plan-artifacts?chain=true` first.
  - `404` → `RenderLegacyAsync`, the original pre-AI-701 recap-only behavior, preserved
    byte-for-byte (same recap call, same "plan"/"write"/"edit"/"whats_done" filtering, same
    section headers/wording).
  - `200` with `primary: null` and empty `artifacts` → "No plan found for this session." and
    returns without ever calling recap.
  - `200` with a plan → calls the existing `GET /api/sessions/{id}/recap?chain=true` for
    current-session work rows (`write`/`edit`) and `whats_done` summaries (unchanged), then
    renders "## Plan" with the primary artifact first, followed by any other discovered
    artifacts (server order, newest-first).
    - `content_state: "truncated"` → prefixes with
      `[plan truncated: first {n} of {original_bytes} bytes]` (n = UTF8 byte count of the
      returned content).
    - `content_state: "unavailable"` → renders `[plan content unavailable due to size bounds]`,
      and if the artifact IS the primary, adds an explicit
      "Validation is not possible: the plan content could not be retrieved (exceeds size bounds)."
      line.
- "## What's Done" / "## Instructions" rendering was factored into a shared
  `RenderWhatsDoneAndInstructions` helper used by both the new and legacy paths, so wording
  stays identical between them.

### 2. Core DTOs (`src/Capacitor.Cli.Core/Models.cs`)
- Added `PlanArtifactDto` and `PlanArtifactsResponseDto`, mirroring the server's
  `Capacitor.Plans.PlanArtifact`/`PlanArtifactsResponse` field-for-field (snake_case
  `[JsonPropertyName]` per field). Enum-like fields (`kind`, `source`, `content_state`,
  `confidence`) are modeled as plain `string` — the CLI only compares/displays them, never
  branches on the full server vocabulary, so no local enum type was introduced.
- Registered both types in `CapacitorJsonContext` (region ~line 806).

### 3. `workspace_root` emission (fail-open, via the existing `GitRepository.FindRoot`)
Added to every session-start payload builder that already carries `cwd`:
- `ClaudeHookCommand.cs` (session-start block, using the already-parsed `sessionCwd`)
- `CodexHookCommand.cs` (`HandleSessionStart`)
- `GeminiHookCommand.cs`, `CopilotHookCommand.cs`, `KiroHookCommand.cs`, `PiHookCommand.cs`,
  `OpenCodeHookCommand.cs`, `AntigravityHookCommand.cs` (each vendor's `HandleSessionStart`)
- `ImportCommand.cs` — the historical importer's `startHook` builder (uses the cwd AFTER
  `CwdRemapper.Apply` + `WorktreePathResolver.Resolve`, so a remapped/renamed repo path still
  resolves correctly)

Each site: `if (cwd is not null && GitRepository.FindRoot(cwd) is { } workspaceRoot) ... = workspaceRoot;`
— `GitRepository.FindRoot` already swallows I/O errors and returns `null` when no `.git` is
found, so the field is simply omitted rather than sent as `null`.

**Scope note (concern):** `CursorHookCommand.cs` / `CursorImportSource.cs` were intentionally
left out. Cursor's payload shape carries `workspace_roots` (its own IDE-workspace-folder concept,
not `cwd`) rather than a filesystem `cwd`, and wasn't named in the brief — adding
`GitRepository.FindRoot(workspaceFolder)` there would be a reasonable follow-up but is a
different code shape and wasn't covered by this task's tests.

### 4. Tests (`test/Capacitor.Cli.Tests.Unit/`)
- **New file `ValidatePlanCommandTests.cs`** (6 tests, WireMock-backed, globally
  `[NotInParallel]` since the SUT writes to `Console.Out`, mirroring
  `ClaudeHookStdoutTests`'s established pattern):
  1. Primary artifact renders under "## Plan"; recap still supplies work rows + whats_done.
  2. Empty response (`primary: null`, `artifacts: []`) → "No plan found for this session." and

  3. `404` on plan-artifacts → legacy recap-only rendering (plan/work/whats_done all from one
     recap call); both routes are hit in order.
  4. `404` + no "plan" recap entries → "No plan found for this session." (legacy empty path).
  5. Truncated primary → byte-count marker + truncated content.
  6. Unavailable primary → placeholder + "Validation is not possible" line.
- **`ClaudeHookCommandTests.cs`**: added 2 tests verifying the `workspace_root` wiring
  end-to-end (posted body includes it when `cwd` resolves to a real `.git`-rooted temp dir;
  omits it for a non-repo `cwd` like `/tmp`). `GitRepository.FindRoot` itself already has full
  coverage in `GitRepositoryTests.cs`, so the other 7 hook commands' identical one-liner wasn't
  re-tested per-file.

## Review-fix pass (three findings, local commits only)

### 1. CRITICAL — degraded state never rendered (`ValidatePlanCommand.RenderPlanArtifacts`)
`is_complete == false` on any artifact (not just the primary) was silently dropped — no marker,
no distinction from a normal complete plan. Fixed by adding a per-artifact check, mirroring the
server's `PlanRowRendering` marker text byte-for-byte (em-dash U+2014, single spaces either side,
verified against the server source at
`Capacitor.Server/Sessions/Plans/PlanRowRendering.cs:23`):

```csharp
const string DegradedMarker = "[plan state: unresolved newer revision — last known complete text]";
...
if (!artifact.IsComplete) {
    await Console.Out.WriteLineAsync(DegradedMarker);
}
```

placed immediately before the existing `switch (artifact.ContentState)` block, so degraded
composes WITH truncated (degraded line first, then the byte-count truncation line, then content)
— matching the server's stated ordering. Applied per-artifact (not gated to `isPrimary`) since
`is_complete` is a per-row attribute and the existing switch already operates per-artifact for
`truncated`/`unavailable`.

New tests in `ValidatePlanCommandTests.cs`:
- `Degraded_primary_prefixes_the_plan_section_with_the_degraded_marker` — degraded-only primary →
  marker precedes content.
- `Degraded_and_truncated_primary_renders_both_markers_degraded_first` — degraded + truncated
  primary → degraded marker, then truncation marker, then content, in that order.

### 2. IMPORTANT — `ImportCommand.cs` workspace_root used the raw, unremapped cwd
`ImportSingleSessionAsync`'s `cwd` derivation (`meta.Cwd ?? DecodeCwdFromDirName(...)`) ignored the
already remap-/worktree-resolved value the import flow computes up front into the `sessionCwds`
dictionary (populated in `ResolveTranscriptReposAsync` at ~line 1988 and the Cursor branch at ~line
573). This meant `workspace_root` (and repo detection) silently used a stale/nonexistent path for
any session whose recorded transcript cwd needed a `cwd_remap` or worktree-attribution fix-up —
the exact case the missing-cwd report exists to surface.

Fixed by threading `sessionCwds` (as `IReadOnlyDictionary<string,string>?`, optional, default
`null` to keep existing call sites/tests source-compatible) through `ImportChainsAsync` →
`ImportSingleSessionAsync`, and preferring it in the cwd derivation:

```csharp
var cwd = sessionCwds is not null && sessionCwds.TryGetValue(session.SessionId, out var resolvedCwd)
    ? resolvedCwd
    : meta.Cwd ?? SessionImporter.DecodeCwdFromDirName(session.EncodedCwd);
```

Both `ImportChainsAsync` call sites in `HandleImport` (TTY and non-TTY branches) now pass the
`sessionCwds` dictionary that was already in scope. This also fixes repo detection
(`RepositoryDetection.DetectRepositoryAsync(cwd, ...)`) consistency for the same reason, as a
side effect — same variable, same bug.

New test in `ImportChainsTests.cs`:
`ImportChainsAsync_derives_workspace_root_from_the_remapped_cwd_not_the_raw_meta_cwd` — session's
`Meta.Cwd` points at a nonexistent path, `sessionCwds` maps the session id to a real temp dir with
a `.git` marker; asserts the POSTed `session-start` body's `workspace_root` (and `cwd`) equal the
resolved dir, not the raw one. Full existing `ImportChainsTests` suite (6 pre-existing tests) still
passes unchanged since the new parameter is optional.

### 3. MINOR — multi-artifact rendering-order test added
New test `Primary_not_first_in_artifacts_array_still_renders_first_then_others_in_server_order` in
`ValidatePlanCommandTests.cs`: a response with `primary` (`is_primary: true`) placed SECOND in the
`artifacts` array (between two other artifacts), plus the primary itself duplicated inside
`artifacts` (as a real server response would send it — `artifacts` is the full discovered set).
Asserts primary's content renders first, then the two others in the array's own order, and that
the primary's content is not duplicated in the output (existing `ordered` list construction in
`RenderPlanArtifacts` already de-dupes by `ArtifactId` before prepending primary — this test locks
that behavior in, since no prior test exercised more than one artifact).
